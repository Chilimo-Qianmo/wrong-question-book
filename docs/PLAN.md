# 错题集生成器 · 架构升级方案（v2）

> **实施状态：已完成。** 引擎、API、Vue3 界面、打包脚本、回归测试均已落地并通过实测（见附录 A）。

> 目标：把「tkinter 单文件脚本 + OCR 猜版面」升级为「双通道 PDF 解析引擎 + Vue3 前端 + 本地 API 服务」，
> 修复已实测确认的识别缺陷，并让电子版试卷做到零 OCR、零版面猜测。

---

## 0. 现状与问题回顾（决定改造范围的依据）

已实测确认（详见上一轮评审）：
- 电子版试卷（有文字层）被强行 OCR，产生坐标抖动、图注混入、表格错乱；
- 扫描版试卷的表格检测条件过严，表格文字混进题干；
- 题号漏识别会把后续整段吞并或截断，且无任何告警；
- OCR 缓存不绑定试卷，会整套串卷；
- 配置快路径缺 options 就丢光选项；配置查找按文件名子串匹配且永远命中最早那份；
- 界面是 tkinter 单窗口，两文件耦合，无法承载「来源标注 / 置信度 / 缺口告警 / 图表预览」等新交互。

---

## 1. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| PDF 路由 | 自研 pdf_router（探测文字层） | 电子/扫描/混合三种卷自动分流 |
| 电子版解析 | pdfplumber（MIT，已装） | 行聚合/表格结构化/图片 bbox 一次到位 |
| 扫描版解析 | pypdfium2 渲染 + RapidOCR（沿用） | 保持现有依赖 |
| 扫描版表格 | OpenCV 自适应阈值+形态学线检测（已装） | 实测命中题10/题14 表格，零新增依赖 |
| 后端 | FastAPI + uvicorn（已装） | 原生 SSE 进度流；OpenAPI 自文档 |
| 前端 | Vue 3 + Vite + TypeScript + Pinia | 组件化承载核对向导 |
| 桌面外壳 | 默认自动打开浏览器；可选 pywebview | 零新增依赖为默认 |
| 打包 | PyInstaller，web/dist 作为数据打包 | 保持单 exe 交付形态 |

## 4. 最后达成的效果（终态）

1. **一份代码吃两种卷**：电子版走文字层（快速精确，含表格与配图），扫描版走 OCR + OpenCV，用户无感知。
2. **识别结果可信可视**：每题标注来源与置信度，缺口/告警/被忽略文本全部显式呈现。
3. **配图与表格自动化**：电子版插图与表格自动抽取归属，人工只需抽查。
4. **工程可维护**：后端按职责拆分 `app/core/*`（17 个模块 3055 行），前端组件化（3683 行）。
5. **交付形态不变**：双击 exe / 启动.bat → 浏览器界面 → 选文件 → 生成归档。
6. **可回归**：`tests/regression.py` 对三份试卷做快照对比。

### A4. 打包 exe 验收（v2.0.1，264MB）

```
[1] /api/health  -> ok, version 2.0.1，pdfplumber/rapidocr/opencv/docx 全部可用
[2] 电子版识别    -> 16 题, 0.5s（pdfplumber 打包可用）
[3] 扫描版识别    -> 15 题, 47s, 缺口 [3→4]（onnxruntime + RapidOCR 模型打包可用）
[4] 生成 Word    -> 学生 50 人 / 文档 50 份，归档到 14班/20260911-…（python-docx 打包可用）
[5] 合并         -> copied=50
```

**v2.0.1 修复**：打包环境下 `cache.code_signature()` 会扫描 `app/core` 目录，
而冻结后源码已进 PYZ、磁盘上不存在该目录，导致「识别失败：WinError 3 系统找不到指定的路径」。
已改为：冻结环境用应用版本号、源码环境用代码指纹，并保证缓存层任何异常都不影响识别。

### A5. 已知限制

1. 扫描件左侧竖排「准考证号/姓名」偶尔会被 OCR 并进正文（本卷实测影响第 1 题）。
   缓解：核对页会高亮告警；从根本上建议提供电子版 PDF。
2. 扫描件的插图区域没有自动识别（无文字层、无矢量信息），图注可能混入题干。
3. OpenCV 线框表格在单元格划分上会留下空列（第 14 题表格首尾各有空列），可在核对页手工调整。
4. 目前只有「选择题」识别；非选择题（大题）不在范围内，与 v1 一致。
